## Commencer par un skill

Un skill est un ensemble ciblé d’instructions, souvent un `SKILL.md` accompagné de références ou de scripts. Il décrit une méthode répétable.

Omni conserve son chemin et son contenu au lieu de traiter le texte comme un simple compteur.

- Lisez le skill dans `Contenu`.
- Gardez les références avec le skill si elles participent à son comportement.
- Capturez seulement après vérification de la provenance.

## Regrouper les skills dans un plugin

Un plugin réunit des skills, commandes, hooks ou configurations MCP liés. Dans le canvas de la marketplace, ses skills sont regroupés.

Choisissez `Plugins et vitrines` pour lire les descriptions des plugins et leurs actions de publication.

- Utilisez `Gérer les skills`, puis `＋ Ajouter des skills` dans un projet.
- Lisez chaque nœud de skill.
- Gardez la provenance du package visible.

## Publier une marketplace

Une marketplace est une source locale de packages. Enregistrez-la depuis `Espace de travail` avec `＋ Ajouter`, puis `Marketplace`, en choisissant le type de source adapté.

Omni observe ses vrais fichiers et affiche la disponibilité avant toute assignation.

- Pour une première source personnelle, choisissez `Une autre marketplace à moi`.
- Utilisez `Source externe` pour le dépôt de quelqu’un d’autre.
- Actualisez quand les fichiers changent hors d’Omni.

## Garder une source de vérité

La marketplace est canonique ; les projets reçoivent des assignations. Claude Code et Codex partagent le contenu compatible via leurs projections natives.

Historique et Git montrent deux niveaux différents du même changement local.

- Lisez les origines observées des skills et les pastilles d’agents.
- Lisez la sélection ou la confirmation avant son action d’écriture.
- Lisez le reçu après approbation.

## Avant d’agir

Commencez par la page observée, pas par une hypothèse sur le système de fichiers. La route et son en-tête disent quelle cible est dans le périmètre d’Omni.

- Lisez le titre et l’onglet actif.
- Préférez l’action nommée au raccourci.
- Gardez le chemin local pour la comparaison.

## Vérifier la frontière

Toute prévisualisation reste en lecture seule jusqu’à l’action d’approbation. Un blocage ou une indisponibilité est une preuve qui demande une autre décision.

- Traitez une racine introuvable comme indisponible.
- Traitez un conflit comme un arrêt.
- Gardez le nom du harness près du chemin.

## Garder la trace

Après une écriture, Historique conserve la trace des opérations. Le reçu et le commit Git se complètent pour rendre une restauration délibérée.

- Lisez les fichiers du reçu.
- Comparez les modifications récentes avant de restaurer.
- Revenez à la source de vérité pour le changement suivant.

## Une vérification régulière

Rouvrez la source et le projet quand les conventions de votre harness changent. Cette courte revue relie l’opération suivante aux preuves locales actuelles.

- Actualisez la racine observée.
- Lisez les chemins modifiés.
- Choisissez une seule action délibérée.
