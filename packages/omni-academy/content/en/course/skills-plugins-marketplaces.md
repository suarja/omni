## Begin with a skill

A skill is a focused instruction set, often a `SKILL.md` plus references or scripts. It describes a repeatable way of working.

Omni observes its path and content instead of treating the text as an opaque count.

- Read the skill in `Content`.
- Keep references beside the skill when they are part of its behavior.
- Capture only after checking provenance.

## Group skills in a plugin

A plugin groups related skills, commands, hooks, or MCP configuration. In the marketplace canvas, its skills are grouped together.

Choose `Plugins and storefronts` to inspect plugin descriptions and publication actions.

- Use `Manage skills`, then `＋ Add skills` in a project.
- Read each skill node.
- Keep package provenance visible.

## Publish a marketplace

A marketplace is a local source of packages. Register it from `Workspace` with `＋ Add`, then `Marketplace`, and choose the appropriate source type.

Omni observes its real files and displays availability before a project can receive an assignment.

- For a first personal source, choose `Another marketplace of mine`.
- Use `External source` for someone else’s repository.
- Refresh when files change outside Omni.

## Keep one source of truth

The marketplace is canonical; projects receive assignments from it. Claude Code and Codex can share compatible content through native projections.

Activity and Git show different layers of the same local change.

- Read the observed skill origins and agent chips.
- Read the selection or confirmation before its write action.
- Read the receipt after approval.

## Before you act

Start with the observed page, not an assumption about the filesystem. The current route and its head tell you which target Omni has in scope.

- Read the page title and the active tab.
- Prefer the named action over a shortcut.
- Keep the local path available for comparison.

## Check the boundary

Every preview is read-only until its approval control is chosen. A blocked or unavailable state is evidence that needs a different decision.

- Treat a missing root as unavailable, not empty.
- Treat a conflict as a stop condition.
- Keep the harness name beside the path.

## Keep the trail

After a write, Activity holds the operation history. The receipt and Git commit complement each other and make a later restore deliberate.

- Read the files in the receipt.
- Compare later edits before restoring.
- Return to the source of truth for the next change.

## A weekly check

Re-open the source and project when your harness conventions change. This small review keeps the next operation tied to current local evidence.

- Refresh the observed root.
- Read the changed paths.
- Choose one deliberate next action.
